# ScholarPath integration plan - Phase One findings

> **Status update (2026-10-12).** This is the Phase One plan, written before implementation. What was built follows it with these
> differences: multi-valued attributes are stored relationally (`scholarship_values`) instead of PostgreSQL arrays, so every query is testable on SQLite
> without a PostgreSQL server; there is an extra `scholarship_criteria.origin` column (ETL rows are replaced on re-import, reviewer rows never are);
> the importer is `python -m app.scripts.import_scholarships`; `GET /api/v1/meta/filters` exists; decisions 1-4 below were implemented as the stated defaults.
> The database itself is still **not created or migrated** - see the README section "Configure PostgreSQL Later". Reconciliation of the data files:
> `docs/data-reconciliation.md`.

Written after a read-only inspection of `scholarpath-data` (ETL), `scholarpath-frontend` (Lovable UI), the
machine, and the (previously non-existent) backend folder. Everything below is based on the actual files.
Items marked **DECISION** need an answer from the project owner; a safe default is stated for each.

## 4. Proposed PostgreSQL schema (stage 2)

Native PostgreSQL types: `text[]` for filterable lists (with GIN indexes), `jsonb` only for heterogeneous data.

**`scholarships`** - one row per ETL record, mirrors the ETL faithfully (nulls stay null)

| Column | Type | Notes |
|---|---|---|
| `id` | bigint identity PK | internal |
| `scholarship_id` | varchar(64) **unique**, not null | the stable ETL id; used in URLs |
| `name` | text not null | records without a name are *failed* by the importer |
| `provider_name`, `application_procedure`, `award_amount_text`, `review_notes` | text null | |
| `scheme_type` | varchar(16) null, CHECK `central/state/other` | |
| `government_level`, `academic_year` | text / varchar(7) null | from `extra_attributes` / ETL |
| `minimum_percentage` | numeric(5,2) null, CHECK 0-100 | |
| `maximum_family_income` / `income_comparator` | numeric(14,2) null CHECK >= 0 / varchar(2) null (`<`, `<=`) | missing is never 0 |
| `award_amount_min/max` | numeric(14,2) null, CHECK >= 0 and min <= max | |
| `application_open_date`, `application_deadline` | date null, CHECK deadline >= open | |
| `education_levels`, `eligible_courses`, `eligible_states`, `eligible_categories`, `eligible_genders` | text[] not null default `{}` | `{ALL}` = explicit "all"; `{}` = source silent. GIN on states, categories, levels |
| `required_documents`, `eligibility_rules` | text[] not null default `{}` | display text |
| `official_url`, `source_url`, `source_name` | text null | |
| `source_type` | varchar(32) not null | |
| `extracted_at` | timestamptz not null | |
| `last_verified_at` | date null | |
| `verification_status` | varchar(16) not null default `pending`, CHECK 4 values | preserved from the ETL, never upgraded by the importer |
| `etl_validation_status`, `etl_issue_codes`, `duplicate_group_id` | varchar / text[] / varchar | |
| `source_file`, `source_sheet`, `source_row`, `source_record_id` | provenance | |
| `extra_attributes` | jsonb not null default `{}` | |
| `created_at`, `updated_at`, `last_import_run_id` | timestamptz / FK | |

**`scholarship_criteria`** - individual eligibility criteria (where review status and evidence attach)

`id`, `scholarship_id` FK (cascade), `criterion_type` (`education_level|state|category|gender|course|minimum_percentage|maximum_family_income|other_rule`),
`label`, `operator` (`in|gte|lte|lt|text`), `required_value` jsonb (`{"values":[..]}` / `{"value":350000,"comparator":"<"}` / `{"text":".."}`),
`is_mandatory` bool, `review_status` (`unreviewed|reviewed|disputed`), `evidence_text`, `evidence_url`, `source_ref`, `display_order`.
The importer derives these rows deterministically from the scholarship fields (re-derived inside the same
transaction on every upsert). The ETL has **no per-criterion citations, mandatory flags or review status**, so:
`evidence_text`/`evidence_url` stay null (only `source_ref` = ETL file+row is set), `review_status = unreviewed`,
and `is_mandatory = true` is a documented interpretation (these canonical fields are, by definition, the
conditions of eligibility). Nothing is cited that the data does not contain.

**`import_runs`** - audit of each import: started/finished, source file name, SHA-256, format, `inserted/updated/unchanged/skipped/failed`, status, error text.

## 5. Proposed API contract

| Endpoint | Notes |
|---|---|
| `GET /health`, `GET /health/db` | **Done** (stage 1). |
| `GET /api/v1/scholarships` | `q`, `state`, `education_level`, `category`, `gender`, `scheme_type`, `student_percentage`, `student_income`, `min_award`, `verified_only`, `sort` (`name`, `amount_desc`, `deadline`, `recently_verified`), `page`, `page_size` (default 12, max 50). Validation: Pydantic v2 request models (ranges, enums, max lengths); structured error bodies; CORS from `CORS_ORIGINS`.

## 6. Eligibility semantics (stage 5)

Pure, DB-free, independently tested function `evaluate(profile, scholarship_criteria, verification)`.

Per criterion: `pass` (rule known, student value known, satisfied), `fail` (confirmed mismatch), `missing`
(student did not supply the value), `unable_to_verify` (rule is ambiguous/free text or cannot be compared).

| Criterion | Rule |
|---|---|
| State | `{ALL}` -> pass; student state in list -> pass; else fail. Student "Other"/blank -> missing. |
| Category | `{ALL}` -> pass; in list -> pass; known category not in list -> fail; blank / "Prefer not to say" -> missing. Source silent (empty) -> unable_to_verify (absence of a rule is not "open to all"). |
| Gender | list covers the student -> pass; `FEMALE`-only and student male -> fail; "Prefer not to say" -> missing. |
| Minimum percentage | numeric rule: `student >= value`. Board-specific text -> unable_to_verify. |
| Maximum family income | numeric rule honouring the `<` (strict) vs `<=` comparator. Text-only rule -> unable_to_verify. |
| Education level | student level mapped to ETL tokens (`Class 10`->`10`, `Class 12`->`12`, `UG`, `PG`). A listed match -> pass. **No match -> unable_to_verify, never fail**, because the ETL notes that token `12` means "completed Class 12" for some schemes and "studying Class 12" for others. |
| Course | `{ALL}` -> pass; otherwise unable_to_verify (free-text course vs tokens such as `B.Tech.MBBS` cannot be matched reliably). |
| Other source conditions | each `eligibility_rules` string -> `unable_to_verify`, quoted as stated. |

Outcome:

* `eligible` - all applicable mandatory criteria `pass` **and** the scholarship is `verified` with reviewed criteria.
* `not_eligible` - at least one mandatory criterion `fail` on a `verified`, reviewed scholarship.
* `cant_tell_yet` - everything else.

**Consequence worth knowing now:** all 34 records are `pending` and every derived criterion is `unreviewed`, so the
real data can only ever return `cant_tell_yet`. Per-criterion statuses are still computed and shown, labelled
"based on unreviewed data", plus an `indicative` hint (`all_listed_criteria_met` / `some_criteria_not_met` / `incomplete`)
so the explanation is useful without declaring eligibility. `eligible` / `not_eligible` are exercised in the
tests with synthetic verified fixtures. **DECISION 2** confirms this strict behaviour.

## 7. Visibility of unverified records

All 34 records are `pending`. "Keep unverified records out of public verified-scholarship results" is implemented as an
explicit `verified_only` flag: `verified_only=true` returns only `verified` records (today: none). **DECISION 1**: what
the default list shows. Recommended default: **show all non-rejected records, each clearly labelled "Unverified"**,
plus a "Verified only" toggle. Otherwise the milestone "frontend fetches real scholarship data" would display an empty
list until a reviewer verifies records. Nothing is ever marked verified automatically.

1. **Default visibility of unverified records** (section 7). Default used until answered: show all non-rejected, labelled Unverified, with `verified_only` available.
2. **Strict eligibility** (section 6): unverified rules can never produce `eligible`/`not_eligible`. Default used: strict.
3. **Education options**: add Class 8 / 9 / 11 / Diploma (and ITI) to the profile form so real records can be matched. Default used: add them (small, flagged UI change).
4. **Provider filter** -> replaced by Central/State. Default used: yes.
5. **PostgreSQL credentials**: create the role/database with the commands in `README.md` and put `DATABASE_URL` in `.env`. Stage 2-5 development proceeds on the isolated throwaway server meanwhile; nothing is claimed about *your* database until `/health/db` says `ok`.

## 10. Risks

* **Application Control policy.** pandas 3.0.6's compiled module was blocked earlier. Tested now: `psycopg` binary, `pydantic_core`, `SQLAlchemy` C extensions, `uvicorn` all load fine. **Not yet tested:** Next.js's native SWC binary and Tailwind v4's native engine (`lightningcss`, `@tailwindcss/oxide`) - the first thing stage 6 verifies. If they are blocked, I will not bypass the policy; I will fall back (e.g. Babel-based Next.js compile / PostCSS-only Tailwind v3) and tell you.
* **Lovable sync.** The original frontend is the fallback and stays untouched; nothing is installed inside it.
* **ID stability.** ETL ids hash name+provider+government level, so editing those in the source changes the id (saved items and reviewer decisions then become unmatched; the importer reports it rather than guessing).
* **No deadlines in the data.** Deadline-driven UI cannot become "real" until a source provides them.
